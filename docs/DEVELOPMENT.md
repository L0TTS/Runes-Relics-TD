# Runes & Relics: TD — структура и совместная работа

Дата: 5 ноября 2026 года.

Документ содержит согласованные порядок совместной работы, дерево каталогов и зависимости сборок. Открытые настройки перечислены отдельно. Технический стек описан в [TECHNICAL.md](TECHNICAL.md), правила агентов — в [AGENTS.md](../AGENTS.md).

## Согласованный порядок работы

- Unity-проект располагается в корне существующего репозитория. Документация остаётся в docs/.
- Собственные код и игровые ресурсы находятся под Assets/_Project/. Сторонние ассеты хранятся отдельно от собственных ресурсов.
- Каталоги создаются по мере появления содержимого.
- main содержит проверенное общее состояние. Каждая задача выполняется в отдельной короткой ветке.
- Изменения проходят через PR с описанием результата и выполненных проверок. Взаимное ревью обязательно для кода, общих настроек и контрактов модулей.
- До начала работы разработчик и его агент обозначают задачу и затрагиваемые файлы. Одну сцену или префаб одновременно редактирует один человек.
- Настройки Unity и версии пакетов меняются отдельной задачей, чтобы второй разработчик мог синхронно обновить окружение.
- Файлы .meta хранятся вместе с соответствующими ресурсами.
- Для крупных бинарных ресурсов выбран Git LFS; начальные форматы перечислены ниже. Объёмы и ограничения хранения проверяются до подключения. На момент записи Git LFS не настроен.
- Порядок веток и PR не отменяет правило: агент делает коммиты, push и публикации только по запросу пользователя или в рамках отдельно согласованной автоматизации.

Обязательное ревью здесь означает согласованный процесс; настройки защиты ветки и права участников в GitHub этим документом не изменены.

## Согласованное дерево проекта

Статус: принято пользователем 5 ноября 2026 года. Ниже целевая схема, каталоги ещё не созданы. Существующая документация сохраняется; приведены только основные группы.

```text
<корень репозитория>/
  AGENTS.md
  README.md
  docs/
  Assets/
    _Project/
      Code/
        Simulation/
        Content/
        Presentation/
        Persistence/
        Steam/
        Bootstrap/
      Editor/
      Tests/
      Scenes/
      Prefabs/
      Content/
      Art/
      Audio/
      UI/
      Localization/
      Settings/
    ThirdParty/
  Packages/
  ProjectSettings/
```

Code/Content/ содержит типы ScriptableObject, описание контента и код его преобразования; Content/ вне Code/ — экземпляры данных. Art/ — собственные модели, материалы, текстуры и анимации. Presentation/ — код отображения и ввода, UI/ — ресурсы интерфейса. Это различие отделяет исходники от данных и ресурсов.

ThirdParty/ — каталог для сторонних ресурсов, если поставщик позволяет такое размещение. Структуру пакетов, устанавливаемых через Package Manager, не переносим вручную в этот каталог.

Editor/ содержит инструменты, требующие UnityEditor. Только редакторские части подготовки контента размещаются в Editor-only сборках; доступные игре определения данных не зависят от UnityEditor.

Steam/ и его зависимости появляются при реализации согласованной интеграции; сейчас пустой модуль и заглушки не создаём. Детализация Tests/ выполняется под фактические тестовые сборки. Packages/ и ProjectSettings/ формируются при создании Unity-проекта.

## Согласованные сборки и зависимости

Статус: принято пользователем 5 ноября 2026 года. Префикс собственных сборок — RunesRelics. Таблица относится к собственным runtime-сборкам; зависимости от Unity и согласованных пакетов перечисляются при реализации.

| Сборка | Ответственность | Прямые зависимости от собственных runtime-сборок |
| --- | --- | --- |
| RunesRelics.Simulation | Состояние и системы боя, проверка команд, контракт состояния для сохранения | Нет |
| RunesRelics.Content | Определения контента и подготовка данных для симуляции | Simulation |
| RunesRelics.Presentation | Камера, ввод, интерфейс и отображение состояния | Simulation, Content |
| RunesRelics.Persistence | Чтение и запись JSON, восстановление через согласованный контракт | Simulation |
| RunesRelics.Steam | Будущая интеграция Steam и адаптация сетевых команд | Simulation; детали после выбора сетевого пакета |
| RunesRelics.Bootstrap | Создание систем и связывание зависимостей при запуске | Все необходимые runtime-модули; Steam только после его подключения |

Simulation не зависит от интерфейса, файлового хранилища, Steam или редактируемых ScriptableObject. При этом она использует Unity.Entities и подходящие математические типы: переносимость без Unity не является требованием.

Presentation передаёт действия через проверяемые команды, а не меняет боевое состояние напрямую. Persistence работает с отдельным представлением сохранения, а не сериализует сцену или ECS World. Конкретный состав контракта определяется требованиями; отдельную общую сборку Core не вводим без необходимости.

Редакторские и тестовые сборки ссылаются на нужные runtime-модули. Обратных зависимостей runtime → Editor/Tests нет. Границы сетевого адаптера пересматриваются при выборе пакета; таблица не утверждает собственную реализацию сетевого стека.

## Ветки, PR и координация задач

Статус: принято пользователем 5 ноября 2026 года.

- Ветки задач: feat/<задача>, fix/<задача>, docs/<задача>, chore/<задача>. Новая задача начинается от актуального main.
- PR сливается через squash merge: одна завершённая задача даёт один коммит в main. После слияния ветку больше не используем.
- Перед ревью описаны результат и выполненные проверки; проект компилируется, относящиеся к изменению тесты проходят. Для изменений графики и интерфейса прилагается скриншот или короткая запись.
- До начала задачи обозначаются исполнитель, область изменений и занятые сцены/префабы. Если задачи пересекаются, сначала согласуется общий контракт.
- Учёт задач и статусов ведётся через GitHub Issues и GitHub Projects, по правилам ниже. Эти правила не дают агентам разрешения самостоятельно отправлять сообщения другим людям.
- Согласованный порядок не является разрешением на коммиты, push или слияние текущих изменений: для этих действий сохраняется требование запроса пользователя либо отдельно согласованного порядка.

## Начальные форматы Git LFS

Статус: принято пользователем 5 ноября 2026 года; правила отслеживания ещё не применены.

- Модели и исходники графики: .fbx, .blend, .psd.
- Изображения: .png, .tga, .jpg, .exr.
- Звук: .wav, .ogg, .mp3.
- Код, документация, .meta, текстовые сцены и префабы хранятся в обычном Git.
- Для .asset учитывается фактический формат; правило на все .asset без разбора не утверждено.
- Правила LFS сохраняются в .gitattributes. Новые расширения согласуются отдельно.
- Доступный объём LFS-хранилища, ограничения передачи и установка у обоих разработчиков проверяются до подключения. Список расширений не утверждает расходы на дополнительные квоты.

## Учёт задач в GitHub

Статус: принято пользователем 5 ноября 2026 года; Issues и доска пока не созданы в рамках этого обсуждения.

- Одна задача — одна Issue. В ней указываются исполнитель, ожидаемый результат, критерии готовности, затрагиваемые файлы и зависимости.
- Доска GitHub Projects: Очередь → Готово к работе → В работе → Ревью → Завершено.
- Заблокированная задача получает метку blocked с объяснением причины.
- Метки области: concept, code, art, infrastructure, bug.
- Разработчик по концепции и аналитике и его агент выполняют задачи с изменениями только в docs/, в соответствии с AGENTS.md. Реализация относится к техническому разработчику.
- Если требование не утверждено, зависящая от него задача реализации остаётся заблокированной. Issue ссылается на документацию; согласованные требования хранятся в docs/, а не только в карточках задач. PR ссылается на соответствующую Issue.

## Обновление рабочих веток

Статус: принято пользователем 5 ноября 2026 года.

- Перед новой задачей локальный main обновляется через fast-forward; новая ветка создаётся от актуального main.
- В существующую рабочую ветку актуальный origin/main вливается обычным merge. Обязательный rebase и force push не входят в согласованный порядок.
- Ветка обновляется перед ревью и повторно перед слиянием, если main изменился.
- После разрешения конфликтов повторяются проверки, относящиеся к изменениям. Изменения других участников сохраняются.
- В main задача по-прежнему вливается через squash merge. Способ обновления рабочей ветки не меняет способ слияния PR.

## Внутренние тестовые сборки

Статус: принято пользователем 5 ноября 2026 года. Получатели первых сборок — только два разработчика команды.

- На первом этапе технический разработчик собирает Windows-билд вручную на ПК пользователя из проверенного коммита main.
- После короткой проверки запуска полный состав Windows-билда упаковывается в ZIP и загружается вложением в GitHub Release с отметкой pre-release в приватном репозитории.
- К сборке прилагаются версия (например, 0.1.0-test.1), хеш коммита, список изменений, известные проблемы, сценарии проверки и сведения о совместимости сохранений.
- Ошибки регистрируются в Issues с версией сборки, шагами воспроизведения, ожидаемым и фактическим результатом, логом или записью.
- Автоматизация рассматривается после появления стабильной ручной сборки. CI, внешние тестировщики и доставка через Steam Playtest пока не согласованы.
- Этот процесс не означает, что билд уже существует или релиз опубликован; публикации требуют запроса пользователя либо отдельно согласованного порядка.

## Что требуется согласовать и настроить позднее

- Объёмы и ограничения Git LFS, установка у обоих разработчиков и применение согласованного списка форматов; правила блокировки бинарных файлов при необходимости.
- Настройки сериализации ресурсов Unity, .gitignore для сгенерированных файлов и одинаковое окружение обоих разработчиков.
- Технические настройки защиты ветки; порядок веток, их обновление, squash merge и критерии ревью уже согласованы.
- Настройка согласованного учёта задач: Issues, метки, доска Projects и доступ участников.
- Подготовка окружения для ручных сборок и выпуск первого внутреннего pre-release по запросу; CI и внешний канал тестирования пока не выбраны.
